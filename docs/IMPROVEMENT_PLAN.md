# JARVIS — план развития

Обновлено: 26.11.2026.

Фокус этого этапа: камера телефона как основная камера JARVIS и стабильное
подключение APK из любой точки мира. Ниже — что уже сделано и что осталось,
с приоритетами P0 (безопасность/связь), P1 (камера и удобство),
P2 (архитектура и инфраструктура).

### Как это работает вместе

1. ПК публикует адрес: `remote.public_url` (named tunnel) → файл
   `data/remote_url.json` (quick/named tunnel) → LAN-адрес из
   `data/remote_status.json` → локальный URL.
2. UI на ПК генерирует QR с
   `jarvis://pair?url=...&token=...&lan=...&rdvu=...&rdvt=...`.
   QR отдаётся только локальному окну; удалённый браузер получает 403.
3. Приложение сохраняет основной, запасной адреса и параметры
   rendezvous, проверяет хост в диалоге и подключается. Если адрес
   не отвечает, пробует запасной LAN-адрес, затем забирает свежий URL
   из ntfy (`rdvu`/`rdvt`): адрес расшифровывается AES-GCM ключом из
   токена, сохраняется и подключение повторяется без участия
   пользователя. Тот же опрос идёт в `RemoteService`, поэтому адрес
   обновляется и при закрытом приложении.
4. Первый JPEG с телефона приходит на `POST /camera/frame`. Если ПК
   ещё не на источнике `phone`, сервер сам вызывает `set_camera`
   (внутренний bridge, без RPC-политики), перезапускает жесты и
   принимает кадр. Троттлинг — 3 секунды, отключается
   `camera.phone_auto_switch`.
5. Если кадры пропали дольше `camera.phone_timeout` (5 с), поток
   помечается `stale`, а `latest_jpeg`/`snapshot_jpeg` не отдают
   последний старый кадр. Телефон видит «ПК: кадры не доходят» и
   повторяет переключение с backoff 3→30 с.

## P0 — безопасность и связь (следующий этап)

### 1. Персональные токены устройств и отзыв доступа

Сейчас у всех клиентов один `remote.token`. Если телефон потерян,
приходится менять общий токен и перенастраивать все устройства.

- [ ] `remote.devices`: список `{id, name, token_hash, created, last_seen}`.
- [ ] Выдача токена при сопряжении вместо передачи общего токена в QR.
- [ ] RPC/CLI «отозвать устройство» и «показать активные устройства».
- [ ] Аудит: писать `device_id` в журнал авторизаций.
- [ ] Ограничение срока жизни pairing-ссылки (например, 10 минут,
      одноразовый код обмена на токен устройства).

Критерий готовности: потерянный телефон отзывается одной командой,
остальные устройства продолжают работать.

### 2. Усиление транспорта

- [ ] Режим «только HTTPS»: при заданном `remote.public_url` отклонять
      вход по HTTP, добавить HSTS и `Strict-Transport-Security` для
      ответов через туннель.
- [ ] Проверять `Origin`/`Host` для RPC и `/camera/frame`, чтобы
      уменьшить риск CSRF/DNS-rebinding при прямом доступе по LAN.
- [ ] Постоянный учёт неудачных авторизаций (сейчас rate-limit
      в памяти) — файл/БД, чтобы перезапуск не сбрасывал блокировки.
- [ ] Опционально: allowlist устройств по отпечатку приложения.

Критерий готовности: публичный адрес не принимает небезопасные запросы,
блокировки переживают перезапуск.

### 3. Приватность камеры

- [ ] Индикатор на ПК «камера телефона активна» с кнопкой немедленного
      отключения (сейчас статус есть в настройках камеры, но нужен
      заметный баннер).
- [ ] Уведомление на телефоне при каждом включении трансляции.
- [ ] Автостоп трансляции при сворачивании приложения дольше N минут
      (опция).

## P1 — камера и удобство

### 4. Качество под реальный канал

- [ ] Адаптивный FPS/JPEG: измерять время `POST /camera/frame` и
      снижать качество при росте задержки, повышать при запасе.
- [ ] Пресеты «экономия / баланс / качество» в Android-приложении.
- [ ] Ограничение полосы на сервере (`camera.max_fps`,

- [ ] Показывать на телефоне реальный размер кадра, fps и задержку
      (часть данных уже есть).

Критерий готовности: на мобильном интернете поток остаётся плавным,
на Wi-Fi — максимальное качество.

### 6. Камера и жесты

## Проверка текущего этапа

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
.\.venv\Scripts\python.exe -m pytest tests -q --cov=app --cov-fail-under=50
.\.venv\Scripts\python.exe -m compileall -q app launcher.py launcher_web.py launcher_remote.py tests
.\.venv\Scripts\python.exe -m ruff check app tests launcher.py launcher_web.py launcher_remote.py scripts
& "$env:USERPROFILE\gradle-8.9\bin\gradle.bat" -p android assembleDebug
```

Ручная проверка:

1. Запустить JARVIS обычным способом (`scripts\start.ps1`) — в логе
   `[TUNNEL] cloudflared запущен (… protocol=http2)` и
   `[TUNNEL] Адрес туннеля подтверждён`; только после этого появляется
   `data/remote_url.json`. Если в логе QUIC-таймауты, проверьте
   `remote.tunnel_protocol` (должен быть `http2`). При выключенном
   автоподъёме — вручную `scripts\start_tunnel_cf.ps1`.
2. В HUD: «Настройки» → «Показать QR для телефона» — QR и ссылка есть,
   в ссылке видны `url`, `token`, `lan`, `rdvu`, `rdvt`; по клику на
   QR открывается крупный оверлей.
3. В приложении: меню «⋮» → «Сканировать QR» → навести на QR →
   подтвердить подключение. Если код не читается: зум 2×/3×,
   коснитесь экрана для фокуса, внизу виден счётчик кадров.
4. Перезапустить JARVIS (quick tunnel получит новый URL), выждать
   до минуты: телефон сам обновит адрес из rendezvous и вернётся
   в ONLINE без повторного сканирования.
5. «Камера» → «Начать трансляцию» → на ПК источник автоматически
   стал `phone`, HUD показывает поток, жесты работают.
6. Выключить Wi-Fi на телефоне на 10 секунд → статус `stale`, vision
   не отдаёт старый кадр; после возврата сети поток восстанавливается.

## Риски и ограничения

- Quick tunnel меняет URL при каждом запуске; rendezvous скрывает это
  от пользователя, но при долгом офлайне телефона (> срока кэша ntfy,
  обычно 12 ч) адрес может не обновиться, пока JARVIS не опубликует
  новый heartbeat. Для гарантированно стабильного адреса — named
  tunnel и `remote.public_url`.
- Rendezvous использует публичный ntfy.sh: топик секретный и адрес
  зашифрован, но факт наличия топика виден сервису. Свой ntfy задаётся
  `remote.rendezvous_url`.
- QR содержит долгосрочный токен. Пока нет персональных токенов,
  не показывайте QR посторонним; после этапа P0 ссылка станет
  одноразовой.
- Встроенный сканер использует камеру телефона; при отказе в
  разрешении остаётся ручная вставка ссылки или системная камера
  через deep link.
- 1080p по мобильной сети может расходовать трафик; используйте
  720p/480p при слабом канале.
